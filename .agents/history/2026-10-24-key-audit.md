# Key and BPM comparison audit

Date: 2026-10-24. Scope: comparison integrity, current tonal evidence, and
confirmed implementation errors. Camelot A/B remains the display convention.

Later follow-up: [local tonality and metadata-free comparison](2026-10-24-local-tonality.md)
adds fresh Traktor/djay controls and the section/overlap implementation. The
untagged runs preserve all 22 keys in each app; the disagreement remains.

## Confirmed defects and fixes

### MP4 integer tempo was written as text

All 22 source recordings contain a `tmpo` data atom with type 1 (UTF-8),
such as the bytes `31 35 30` for the string `150`. The production writer used
`Tag::insert_text(ItemKey::IntegerBpm, ...)`; Lofty 0.22.4's generic Tag-to-Ilst
conversion preserves that as UTF-8 rather than an integer.

`tmpo` is an integer field, as documented by the
[Mutagen MP4 API](https://mutagen.readthedocs.io/en/latest/api/mp4.html).
This is a concrete interoperability defect. It makes pre-analysis tempo
displays unsuitable as detector evidence; it does not by itself establish
the cause of every VirtualDJ post-analysis difference.

The writer now creates a format-specific, two-byte big-endian integer atom
with data type 21. The decimal freeform BPM, key, artwork and opaque DJ atoms
are retained. Old text-form tempo tags are repaired even when the displayed
text already matches. Valid native integer tags do not cause repeated writes.
The comparison copies additionally contain both a native integer `tmpo` and
the legacy text `tmpo` on all 22 files. A first-atom-only check initially missed
five whose integer already matched the requested BPM. File-level validation
caught this; the final repair requires a unique atom and collapses duplicates.
The regression explicitly recreates the generic-tag plus native-companion case.
ID3's text BPM representation remains unchanged. Repair still uses the existing
staged file, encoded-audio check, source-change check and atomic replacement.

### Flat chroma acquired a fabricated key label

The shared estimator sorted 24 tied zero-correlation scores and returned a
key name for a uniform nonzero pitch-class profile. Confidence was zero, but
the displayed name could still suggest a detected key. Invalid numeric data
also entered the correlation calculation.

Both whole-track and overlap estimators now return no key for flat,
negative, nonfinite or overflowing input. Non-flat valid evidence retains the
existing estimator and confidence formula. No empirical decision threshold
or key template was retuned. Analysis version is 25 and order version is 5 so
persisted analyses/order results cannot silently retain the old behavior.

## Current measured evidence

- Reparsed the original Traktor NML, djay accessibility capture and both
  VirtualDJ CSV exports. All 22 title matches, key conversions and BPM values
  agree with the comparison table; no row-joining or Camelot conversion error
  was found.
- Re-read all 22 current original sources and comparison copies. Their MP4
  `mdat` hashes match the prior manifest on every recording. The Traktor/djay
  audit copies' full-file hashes differ from that earlier manifest; the encoded
  audio does not. This audit does not attribute those metadata changes to a
  specific application or timestamp.
- All 44 VirtualDJ input files still match their stored full-file SHA256 values.
- Original-tag and remuxed untagged inputs have identical audio stream
  parameters and packet timing/size records on all 22. Remux did not introduce
  a tempo or duration change. Container/path/cache differences remain controls
  that were not independently isolated.
- Freshly decoded all 22 using the current production analyzer with native
  voice classification disabled. Global keys are unchanged on 22/22. Maximum
  stored-JSON versus fresh BPM difference is below 0.00001 BPM. This validates
  reproducibility, not musical accuracy.
- Twelve global key confidences are below the planner's existing 0.55
  reliability gate. Confidence is an uncalibrated correlation/margin heuristic,
  not a probability or a percentage accuracy.

| Track | Global key | Confidence | Local diagnostic observation |
| --- | --- | ---: | --- |
| Bloom | 8B | 0.017 | 16-second windows choose 7A five times, 7B three, 8B three, 10B once, 8A once |
| Spiritbond | 11B | 0.103 | Detected drop at 52.8–75.2 s chooses 11A at 0.912; whole-track consensus does not validate local labels |
| For You, Always | 12B | 0.007 | 16-second windows split evenly between 12B and 1B, eight each, plus one 7A |
| Offset | 3B | 0.115 | Windows choose 3A eight times, 3B six and 4A once |
| Still Here | 6B | 0.246 | Windows split six each between 6B and 5B |

These are observations from measured chroma, not independently annotated keys
or proof of modulation. Local diagnostic windows aggregate bar chroma by
covered duration; they do not exactly reproduce the raw global frame average
or the RMS-weighted overlap scorer. Sixteen seconds is a diagnostic interval,
not a claim about phrase length. The new `key-audit` example records both
fixed-time windows and detected-section ranges with their chroma and confidence.

## Remaining limits

The current detector measures detuning, interpolated spectral peaks and local
whitening, then compares a whole-track average with fixed major/minor profiles.
It does not separately establish the tonic from bass motion, chord progression
or phrase endings. Window disagreement lowers global confidence but does not
resolve the alternatives. A whole-track label therefore cannot establish the
best key for every overlap, and a high local profile score is not annotated
harmonic truth. The planner already examines local overlap evidence; simply
replacing its labels with the global majority vote would remove that distinction.

Only VirtualDJ received the tag-free control. Explicit reanalysis in Traktor
and djay is useful evidence, but their independence from all imported tags
was not controlled the same way. The three VirtualDJ tempo outliers and the
11 key disagreements therefore remain review candidates. Bloom is a strong
candidate for tonal annotation, not a confirmed D-minor correction.

All 22 recordings were already inspected in earlier work and form a regression
set, not a held-out accuracy benchmark. No listening or expert annotation was
performed in this audit, and no detector was trained to match another product.

## Reproduction and validation

`key-audit OUTPUT.json TRACK...` performs fresh offline analysis and records
the current analysis version and each input's BLAKE3 identity.
`tag-writeback-audit INPUT.json NEW_OUTPUT_DIRECTORY` exercises the production
writer only on newly created copies, verifies encoded audio identity and source
bytes, and requires a second write to be a no-op. Both examples are in their
respective crate's `examples/` directory.

Ignored evidence is under `target/key-compare-20261024/`: raw comparison
exports, `comparison-integrity-audit.json`, `audio-identity-audit.json`,
`packet-timing-audit.json`, `key-audit-fresh.json`, `key-audit-summary.json`,
the VirtualDJ input rechecks, test/build logs, and tag repair results.

- The final production tag writer was exercised on 22 new copies: all source
  hashes and encoded audio identities remained unchanged, and every second
  write was a no-op. Independent atom parsing verified exactly one two-byte
  integer `tmpo` per repaired file; all unrelated ilst atom payloads were
  preserved byte-for-byte. ffprobe verified decimal BPM within 0.0051 BPM of
  the supplied value (two-decimal tag rounding).
- Shared tonal tests cover invalid/flat evidence, valid contrast under scaling
  and background offsets, and Camelot transposition. Tag tests cover integer
  serialization at 75/150/255/256 BPM, preservation, duplicates and idempotence.
- Full workspace tests excluding desktop: 606 passed, 28 ignored, zero failures.
  Final `./dev.sh --build` passed and refreshed the beta.5 development bundle.
  Logs are `audit-workspace-tests-final.log` and `audit-dev-build-final.log`;
  bundle identity is in `audit-build-evidence.json`. `git diff --check` passed.

No formal app installation, release, commit, push or live-library repair was
run. Existing music files are repaired on a subsequent normal metadata write;
this audit modified only its explicitly created test copies. No corrected-tag
native import into the other DJ apps is claimed.
